# Vendetta admin

База игроков с поиском по нику и признакам, карточками и заметками.

## Запуск

```bash
cp .env.example .env   # поменяйте ROOT_NICKNAME/ROOT_EMAIL и ROOT_PASSWORD
make up                # соберёт образ и поднимет postgres вместе с приложением
```

Админка на http://localhost:8080. Рут создаётся при первом запуске из
`ROOT_NICKNAME`/`ROOT_EMAIL`/`ROOT_PASSWORD`; повторные запуски эти переменные
игнорируют. Почта необязательна: вход идёт по нику либо по почте.
Миграции накатываются самим приложением при старте.

Приложение ждёт готовности базы через `depends_on: service_healthy`, поэтому
порядок запуска соблюдается автоматически. Готовность самого приложения
проверяется по `GET /healthz` — он отвечает 200, только если база на связи.

Памятка для тех, кому выдали доступ, — [GUIDE.md](GUIDE.md): вход, поиск,
заметки, а во второй половине — разделы для админов. Она же короткой версией
живёт в самой админке: раздел «Справка» (`/faq`) виден всем авторизованным,
часть ответов в нём показывается только админам.

## Настройки

Всё задаётся в `.env` (см. `.env.example`):

| переменная | по умолчанию | зачем |
|---|---|---|
| `APP_PORT` | `8080` | порт админки на хосте |
| `POSTGRES_PORT` | `5434` | порт базы на хосте, для psql и `make dev` |
| `POSTGRES_USER` / `PASSWORD` / `DB` | `vendetta` | учётные данные базы |
| `DATABASE_URL` | localhost:5434 | только для `make dev`; в docker перекрывается адресом `postgres:5432` |
| `SESSION_TTL` | `168h` | срок жизни сессии |
| `LOG_LEVEL` | `info` | `debug` показывает каждый опрос лобби |
| `COOKIE_SECURE` | `false` | поставьте `true` за HTTPS |
| `TZ` | `Europe/Berlin` | зона для дат в интерфейсе (центральноевропейская) |
| `ROOT_PASSWORD` | — | обязателен, иначе compose не стартует |
| `ROOT_NICKNAME` / `ROOT_EMAIL` | — | нужен хотя бы один; без ника он берётся из почты до `@` |
| `S1914_*` | — | слежение за лобби Supremacy 1914 и автопилот партий, подробности в `.env.example` |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | — | куда сообщать о найденных играх; без них остаётся запись в логе |
| `TELEGRAM_TOPIC_ID` | — | тема группы-форума; для обычного чата и канала не нужен |

Образ двухступенчатый: сборка на `golang:1.25-alpine`, рантайм — `alpine`
с непривилегированным пользователем. На выходе ~22 МБ, внутри один статический
бинарник со вшитыми шаблонами, статикой и миграциями.

| удалять чужую заметку | ❌ | ✅ | ✅ |

| писать обращения в обратную связь | ✅ | ✅ | ✅ |

| заводить и править признаки | ❌ | ❌ | ✅ |
| выдавать доступы (user и admin) | ❌ | ✅ | ✅ |
| повышать и понижать админов | ❌ | ✅ | ✅ |
| блокировать и менять пароли | ❌ | ✅ | ✅ |
| удалять пользователей | ❌ | ❌ | ✅ |
| журнал действий | ❌ | ✅ | ✅ |
| раздел «Игры» (аккаунт Supremacy) | по доступу | по доступу | ✅ |
| выдавать доступ к «Играм» | ❌ | ❌ | ✅ |
| включать автопилот в партии | ❌ | ❌ | ✅ |

Доступ к «Играм» — не ступень в лестнице ролей, а персональный флаг
`users.games_access`: выдаёт и снимает его только рут, на странице «Доступы».
Админу он сам по себе не достаётся, и раздавать его дальше админ не может.
Причина в том, что раздел ходит в игру под общим аккаунтом проекта, а заход
в состав партии игра засчитывает как вход в неё. Рут проходит по роли, флага
ему не нужно.

Рут в системе ровно один — это гарантирует частичный уникальный индекс
`users_single_root`. Рута нельзя понизить, заблокировать или удалить,
в том числе им самим.

Понижение роли, блокировка и смена пароля немедленно убивают все сессии
пользователя.

## Признаки

Признаки живут в таблице `traits` — это справочник, а не колонки; отметки
у игроков лежат в `player_traits`.

У признака есть знак `kind`: `bad`, `neutral` или `good`. Он не участвует
ни в каких расчётах — им красится метка, чтобы «Мультивод» и «Хорошо
играет» различались взглядом, и по нему же справочник сортируется: плохое
сверху.

Шкал риска и лояльности больше нет. Они считались от весов и отвечали на
вопрос «сколько из возможного набрано», а спрашивают у базы другое —
конкретное поведение. Колонка `weight` осталась лежать с прежними числами:
её никто не читает, но когда процент вернётся в новом виде, будет от чего
отталкиваться.

Снятый флаг `is_active` убирает признак из форм, но сохраняет уже
проставленные отметки.

Раздел «Настройки» (`/settings`) — общее для всей админки, только для рута.
Сейчас в нём справочник признаков, рубильник сбора коалиций и счёт открытий
карты; счётчики архива коалиций остались в «Играх», где на них и смотрят.

Открытия карты считаются по `user_map_checks` — той же таблице, что держит
суточный лимит: строка на пару «человек + день». Отдельного журнала для
аналитики не заводили, поэтому в счёт попадает ровно то, за что берётся
проверка, — заход в партию за состоянием; несостоявшийся заход возвращает
её и в счёт не идёт. Рут лимитом не ограничен, но `MapChecks.Record`
отмечает и его открытия: иначе цифра показывала бы всех, кроме самого
активного. Строки живут `domain.MapChecksTTL` (90 дней), окно показа —
две недели.

Справочник правит рут там же: завести признак,
переименовать, сменить знак и порядок, погасить флагом `is_active` или удалить
вместе со всеми отметками. Правки пишутся в журнал (`trait.create`,
`trait.update`, `trait.delete`), а в колонке «Отмечен» видно, скольких игроков
затронет удаление.

Отмечает признаки любой авторизованный — как и заметки: замечает поведение
тот, кто играет рядом, а не тот, у кого есть право править карточку. Поэтому
каждое нажатие уходит в журнал (`player.trait.add` и `player.trait.remove`
с ником и названием признака), а повторное нажатие в него не попадает:
INSERT и DELETE отвечают, изменилось ли что-нибудь на самом деле.

## Структура

```
cmd/server           точка входа
cmd/gameinfo         разовый отчёт по партии Supremacy 1914
internal/config      конфигурация из переменных окружения
internal/domain      роли, правила доступа, признаки
internal/repo        запросы к postgres (pgx)
internal/auth        argon2id, сессии, middleware, CSRF
internal/storage     пул соединений и миграции (goose, embed)
internal/web         роутинг, обработчики, шаблоны и статика (embed)
```

Шаблоны и статика вшиты в бинарник, так что деплой — это один файл плюс
доступный postgres.

## Поиск

Поиск идёт по подстроке игрового ID и ника без учёта регистра (`ILIKE '%q%'`)
и обслуживается GIN-индексами по триграммам `players_nickname_trgm` и
`players_game_id_trgm`. Результаты сортируются: точное совпадение по ID, точное
по нику, затем начинающиеся с запроса, затем остальные. Выдача ограничена
50 записями, ввод отправляется через HTMX с задержкой 250 мс.

Рядом со строкой — фильтр по клану и галочки признаков (`traits` в адресе,
по одной на код). Выбранные признаки складываются: условие сверяет число
совпавших кодов с числом отмеченных, поэтому находятся те, у кого стоят все
галочки сразу. Повторы в адресе отсеиваются — иначе счёт не сошёлся бы ни
у кого. Отмеченные признаки считаются запросом наравне со строкой: с пустым
полем, но с галочкой поиск ищет.

Уникален только игровой ID (`players_game_id_key` по `lower(game_id)`): он
у аккаунта один и навсегда, а ник меняют, и один и тот же ник со временем
встречается у разных людей. Ник поэтому просто индексируется — `btree` по
`lower(nickname)` для точного совпадения и триграммы для подстроки. Поле ID
обязательно и при заведении карточки, и при правке: у записей, сделанных до
его появления, оно пустое (в базе `NULL`).

## Карточки заводятся сами

Каждый заход на страницу партии заводит карточку всем её участникам, у кого
игра назвала ник и номер: `Players.ImportSeen` вставляет их одним запросом
с `ON CONFLICT (lower(game_id)) DO NOTHING`. Уже заведённые не трогаются
вовсе — там могут быть чужие правки, а игра рассказывает только ник и ID;
переименовавшийся так и остаётся под старым ником, пока его не поправит админ.

Автор у таких карточек пуст (`created_by IS NULL`) — их завела не рука,
а заход в партию. Миграция `00025` заводит их же задним числом всем, кого
уже видели (`supremacy_players`).

## Личные списки: друзья и враги

Два раздела, устроенные одинаково: `user_friends` и `user_enemies` — таблицы
с составным ключом `(user_id, player_id)` и своим комментарием. Список личный,
поэтому одна карточка бывает у одного в друзьях, у другого во врагах, и это
разные записи разных людей. На признаки игрока списки не влияют.

Общего кода у разделов столько же, сколько общего смысла: одна `repo.Relations`
(отличается именем таблицы), один `relationSection` в вебе и одна разметка
`_relations.gohtml`. Различаются они только словами — `enemyWords`
и `friendWords` в `internal/web/handlers_relations.go`; там же и подписи кнопок
в строке поиска, и цвет пометки.

Добавляют двумя путями: кнопкой в строке поиска (без комментария, ответ
подменяется через HTMX) и в самом разделе — поиск, выпадающий список
совпадений, комментарий. Пустой запрос в разделе ничего не предлагает: подбор
отвечает на набранное, а не показывает базу целиком.

## Обратная связь

Раздел «Обратная связь» (`/feedback`) — обращения тех, кому выдан доступ,
и переписка по ним. Две таблицы: `feedback_tickets` (автор, тема, статус,
даты) и `feedback_messages` (сообщения); имя автора хранится копией рядом
с `author_id`, поэтому удаление пользователя не уносит разговор.

Статуса ровно два, `open` и `closed`. Кто и что может, решает предметная
область (`internal/domain/feedback.go`): чужое обращение постороннему не
показывается вовсе — отвечает 404, а не 403; закрытое поднимает обратно
только новое сообщение автора, ответ админа в закрытое остаётся припиской.

Число рядом с разделом в шапке считается на каждой полной отрисовке
(`feedbackBadge` в `internal/web/templates.go`): админу — сколько обращений
открыто, автору — на сколько его обращений ответили после того, как он
последний раз открывал переписку (`author_seen_at`).

## Игры аккаунта Supremacy

Раздел «Игры» (`GET /games`, по доступу от рута) показывает партии того аккаунта,
под которым админка ходит в Supremacy 1914, — то же, что вкладка «Обзор»
на `game.php`. Данные берутся вызовом `getGames` с `userID` в момент
открытия страницы и никуда не сохраняются; завершённые партии не приходят,
они лежат в архиве (`mygamesMode=archived`). Ответ на этот вызов, в отличие
от лобби, — сразу массив игр, без обёртки с `numGames`.

Клиент игры один на приложение: его делят воркер лобби и этот раздел.
Без `S1914_USER` он не создаётся, и страница прямо говорит, чего не хватает.

## Слежение за лобби

Воркер раз в `S1914_POLL_INTERVAL` берёт список открытых партий и сообщает
о тех, чьё название подходит под `S1914_WATCH_TITLES` (пустой фильтр — все).
Обучающие партии (`[Tutorial] - …`) отсеиваются всегда, до фильтра: они висят
в лобби постоянно и попадали бы в выдачу заодно с настоящими — список
исключений лежит в `skipTitles` в `internal/supremacy/watcher.go`.

## Автопилот в партии

Раздел «Игры» → карточка партии (`GET /games/{id}`, по доступу от рута)
показывает, что админка делает в партии сама. Блок автопилота видит и жмёт
только рут: `POST /games/{id}/hero` и `/hero/run` стоят под его ролью. Пока это один переключатель — навык Мейв
«призвать пехоту»: включённую партию автопилот обходит и жмёт кнопку, а итог
захода пишет в `supremacy_game_tasks.last_result` — он и виден на странице.

Включение переключателя заходит в партию сразу же, не дожидаясь тика воркера:
это тот же заход, что делает автопилот, и он же решает, надо ли жать. Клиент
сначала смотрит, не занята ли героиня размещением (`Army.Deploying`), и если
занята — кнопку не трогает, а возвращает, сколько игрового времени осталось.
Повторное нажатие игра принимает молча и таймер не сбрасывает, поэтому
рапортовать об успехе в этом случае было бы враньём. Включение, «Призвать
сейчас» и заход воркера идут через один и тот же `heroDeploy` и пишут итог
в одни и те же поля.

Пауза между обходами каждый раз своя — случайная величина от
`S1914_HERO_INTERVAL` до `S1914_HERO_INTERVAL_MAX` (по умолчанию 45 и 50
минут). Заход игра засчитывает как вход в партию, и ровные 45 минут круглые
сутки — подпись робота; разброс её стирает, ничего не стоя. Равные границы
дают прежний ровный интервал.

Настройка живёт на партии, а не на пользователе: игровой аккаунт в проекте
один и общий.

Как это устроено под капотом (запрос снят с живого нажатия кнопки в браузере
31.08.2026): активация уходит не сама по себе, а вложенной в
`UltUpdateGameStateAction` — `UltArmyAction` с армией героини и единственной
командой `{"@c":"duc"}`. Команда пустая (ни цели, ни координат) и **заменяет
очередь команд армии**: призыв отменяет марш, ровно как при нажатии руками.
Армию игра требует вернуть в сокращённом виде — номер, размер, владелец,
состав по типам; поле `n` есть только у героини.

Армия с героиней ищется по роли `DEPLOY_INFANTRY` в справочнике типов юнитов
(`allUnitTypes`), а не по номеру типа: в другой партии он будет другим.

Пока идёт размещение, у армии стоит команда `dwc` — повторное нажатие игра
принимает молча и таймер не сбрасывает, поэтому автопилот в этом случае не
жмёт ничего и пишет в итог, сколько осталось.

### Чья страна на странице

«Своё» на карточке партии — это страна смотрящего, а не аккаунта проекта:
игрок ищется среди участников партии по совпадению `siteUserID` с игровым ID
из профиля (`users.game_id`, страница «Профиль»). От него считаются блок
«мои провинции», жёлтая обводка на карте и строка «вы играете за …».

Не нашли — страница показывает партию без «своего» и объясняет, почему:
игровой ID в профиле не указан или человек в этой партии не играет. Личные
списки от этого не зависят, они и так свои у каждого.

Игровой ID в профиле человек заполняет сам, и никто его не проверяет: вписав
чужой, он увидит партию глазами чужой страны. Если это когда-нибудь станет
важно, ID надо будет брать не из профиля, а из карточки игрока, привязанной
к учётке админом.

## Проверенные партии

Открытая страница партии оставляет след в `user_checked_games`: строка на пару
«пользователь + партия», в ней название на момент проверки и дата последней.
Строка на партию, а не на заход, — список отвечает на вопрос «чем я занят
сейчас», а не «когда и куда я ходил». Отметка ставится, как только партия
нашлась, — и на чужую, и на свою до захода внутрь: проверкой считается сам
взгляд на партию. Ошибка записи страницу не рушит, партия просто не всплывёт
наверх списка.

Живёт запись `domain.CheckedGamesTTL` — неделю с последней проверки. Срок
держат в двух местах сразу: страница «Игры» отбирает по нему свежие записи,
а часовая уборка в `cmd/server` (`cleanupCheckedGames`) удаляет отстоявшиеся,
чтобы таблица не росла вечно. Первого хватило бы для вида, второго — для
порядка в базе.

## Карта партии

Кнопка «Заглянуть в партию» рисует карту прямо на странице. Данных для этого
два источника: владельцы провинций приходят в состоянии партии, а очертания —
отдельным статическим файлом `https://static.supremacy1914.com/fileadmin/
mapjson/live/<mapID>@high.json` (около мегабайта, один на карту, кешируется
в памяти процесса до перезапуска).

Состояние партии — самое дорогое, что мы берём у игры: полтора мегабайта
и секунды ожидания. Спрашивают его все — страницы, сборщик коалиций,
автопилот, — и об одних и тех же партиях, поэтому копия одна на всех
(`internal/supremacy/state_cache.go`). Кладёт её `gameState` — единственное
место, где состояние приходит с сервера, — значит, кэш наполняют все разом,
и бот в том числе.

Срок годности копии — полтора игровых часа: `stateFresh` делится на скорость
партии (`Game.Speed()`, запоминается в `speeds` при любом разборе партии).
У x1 это полтора часа, у x4 двадцать две минуты, у x10 девять; про партию
неизвестной скорости берём самый короткий срок. Рут смотрит свежее —
`rootStateFresh`, пятнадцать минут, — но не дольше общего срока. Поход
на сервер идёт по одному на партию (канал `busy`, как у ответа сайта):
двое, открывшие партию разом, ждут один ответ. Потолок кэша —
`stateCacheMax` партий, уходит та, к которой дольше всех не обращались:
сборщик коалиций приносит по пять партий каждые десять минут и без потолка
вытеснил бы то, что смотрят люди.

Показ карты стоит проверки. Их дневное число живёт на пользователе
(`users.map_checks`, по умолчанию 5, меняет рут в «Доступах»), израсходованное
за день — в `user_map_checks` по паре «человек + день». Занимаются проверки
одним запросом с `WHERE used < $limit`: две вкладки одного человека не должны
потратить последнюю проверку дважды. Проверка тратится на любой показ карты,
включая обновление страницы и данные из кэша, и возвращается, если игра
не ответила. Рут вне счёта. День считает приложение по своим часам, а не
база: сутки должны кончаться там же, где кончаются у людей.

Мгновенный ответ из кэша выдал бы, что партию уже кто-то смотрел, поэтому
страница всегда показывает «собираем данные» — ровно столько, сколько
не хватило до обычного времени сбора (`loaderMs`, пять секунд плюс разброс,
минус то, что запрос занял на самом деле). Накрывает карту скрипт: без него
она видна сразу.

Контур провинции лежит в поле `b` как base64: подряд идущие пары uint16
big-endian, уже в координатах карты — масштабировать ничего не нужно (поле
`bp` на них не влияет). Море (`@c: "sp"`) не рисуется совсем: под сушу
подложен фон, и полутысячи лишних многоугольников это экономит. Страница
отдаёт SVG на 367 многоугольников, около 240 КБ.

Провинции раскрашены цветом страны-владельца (`primaryColor` из профиля
игрока), ничейная земля — общим серым, свои обведены жёлтым. Страна, у которой
есть владелец, подписывается один раз — посередине своих владений.

Игроки партии сводятся с базой по игровому ID: в состоянии это `siteUserID`
профиля, в базе — `players.game_id`. Дальше их сверяют с личными списками
смотрящего: враги обводятся красным и подписываются мечом, друзья — зелёным
и рукопожатием, и те и другие перечисляются под картой со ссылками на карточки.
Карточки берутся одним запросом на оба списка. Обводки спорят за провинцию
в понятном порядке: своя важнее вражеской, вражеская важнее дружеской. Списки
личные, поэтому у разных пользователей одна и та же партия помечена по-разному.

## Состав партии с игрового сервера

Лобби и список своих игр отдаёт `index.php`-API, а вот карта, провинции
и игроки лежат на игровом сервере партии (`*-gs-*.c.bytro.com`). Дорога туда:

1. `getGameToken` с `gameID` — возвращает `token` с адресом сервера (`gs`),
   ключом `auth` и `authTstamp`; подписи, как в `index.php`, дальше не нужно;
2. `UltActivateGameAction` — возвращает наш `playerID` в этой партии;
3. `UltUpdateGameStateAction` с вложенным `UltLoginAction` — полное состояние.

В состоянии нас интересуют три блока: `1` — игроки (страна, ник, столица),
`3` — карта (`locations`, где `@c: "p"` суша с владельцем `o`, а `@c: "sp"`
море без владельца), `12` — день партии.

Игровой сервер сверяет версию клиента и на устаревшую отвечает исключением,
в котором сам называет актуальный номер, — клиент его запоминает и повторяет
запрос, так что руками версию править не нужно.

**Такой заход игра засчитывает как вход в партию**, поэтому по таймеру это
не дёргается: только `make game` и только руками. Живая проверка форматов —
`GAME=<id> go test -tags live ./internal/supremacy/`, в обычный прогон она
не входит.
